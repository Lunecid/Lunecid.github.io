## 질문

공유 PM(개인형 이동장치) 서비스는 빠르게 늘었지만 시민 인식은 나쁩니다. 가장 큰 이유는 빠른 속도와 아무 데나 세워 두는 주차입니다. 목표는 주차 질서를 잡으면서도 이용률은 떨어뜨리지 않는 방법을 찾는 것이었습니다.

처음 질문은 "어디에 주차장을 더 둘까"였습니다. 입지 모델을 설계하던 중, 주차 공간을 늘려도 아무 데나 세우는 습관은 남는다고 판단해 질문을 바꿨습니다. 사용자가 제대로 세웠는가, 그리고 어떻게 하면 제대로 세우게 만들 수 있는가.

## 데이터

- **입지 탐색**: 서울 열린데이터광장·공공데이터포털·TAAS의 PM 사고·견인 현황, 전동킥보드 주차구역, 생활인구, 지하철 승하차, 버스정류장, 상권 유동인구, 공공자전거(따릉이) 대여 데이터. 킥보드 이용 데이터는 여러 업체로 나뉘어 있어 구할 수 없었습니다. 그래서 같은 공유 서비스이면서 선행연구에서 유동인구와의 관련이 확인된 따릉이 대여 건수를 대용치로 썼습니다.
- **주차 판정**: Roboflow 공개 데이터로 시작했다가, 직접 찍고 Labelme로 라벨링한 사진으로 바꿨습니다. 증강을 거쳐 1,429장을 학습에 썼습니다.

## 방법

1. **입지 우선순위.** 견인 건수, 대중교통 승하차 인원, 주 이용층(10–30대) 대비 주차구역 수, 대학 수, 상권 밀집도로 자치구 순위를 매겨 강남구를 고르고, 그 안에서 행정동을 좁혔습니다(그림 1, 2).
2. **주차 판정 모델.** 질문을 바꾼 뒤에는 반납할 때 찍는 사진 한 장으로 주차 상태를 판정하기로 했습니다. 라벨 설계를 여섯 번 바꾸며 YOLOv5, YOLOv8, Mask R-CNN을 시험했고, 최종적으로 주차구역(parking)·킥보드(scooter)·바퀴(wheel)를 찾아 구역 안에 있는지, 서 있는지를 판정했습니다(그림 3).
3. **점수 규칙.** 주차 적합도(0–100)와 서 있는지 여부로 점수를 매깁니다. 구역 안에 바르게 세울수록 점수가 커지고(최대 20점), 같은 적합도라면 서 있는 쪽에 2점을 더 주며, 구역 밖은 최저점만 줍니다.
4. **웹 서비스.** Django로 회원가입, 반납 사진 업로드, 누적 점수 랭킹, 업로드 기록을 보는 마이페이지, 현재 위치 지도, 챗봇을 만들었습니다. 발표 때는 Nginx·uWSGI 웹 서버와 MySQL DB 서버를 나눠 구성했습니다.

## 결과

팀은 판정 모델을 학습하고 사진 업로드·랭킹 웹 서비스를 만들었으며, 둘을 잇는 점수 규칙을 설계해 로컬 프로토타입에 구현했습니다. 이 프로젝트로 멀티캠퍼스 기업 요구사항 기반 문제해결 프로젝트에서 최우수상을 받았습니다.

팀이 꼽은 결정적 변화는 모델 교체보다 라벨 단위였습니다. 킥보드와 주차장을 서로 다른 상자로 잡았을 때는 둘의 관계가 학습되지 않았고, 한 상자로 묶자 구역 안과 밖을 구분하기 시작했습니다.

공개 저장소의 웹 서비스는 사진을 올릴 때마다 고정 점수를 쌓는 형태입니다. 판정 모델 학습과 위 점수 규칙은 팀이 따로 만든 로컬 프로토타입(저장소의 training/)에 있습니다.

## 기획자·PM 관점

보상 원칙은 단순하게 잡았습니다. 좋은 행동일수록 보상이 커지고, 구역 밖 주차에는 최저점만 줍니다. 다만 보상이 실제 주차 습관을 바꿨는지는 측정하지 못했습니다. 다시 한다면 같은 기간에 사용자를 무작위로 나눠 점수를 켠 집단과 끈 집단의 주차 품질을 비교하는 A/B 테스트로 효과부터 확인하겠습니다.

## 내 역할과 기여

5인 팀에서 다음을 맡았습니다.

- **웹사이트 구축**: Django 기반 서비스 화면과 기능을 구현했습니다.

## 배운 점

- **질문을 바꾸는 것이 모델을 고치는 것보다 효과가 컸습니다.** 입지 분석만 붙잡고 있었다면 사용자의 주차 행동을 겨냥한 서비스는 설계하지 못했을 것입니다.
- **라벨 설계가 성능을 갈랐습니다.** 모델과 데이터 양도 바뀌었지만, 무엇을 한 단위로 볼지 정하는 일이 결과를 가장 크게 바꿨습니다.
- **보상은 측정 계획과 함께 설계해야 합니다.** 보상 구조는 설계했지만, 효과를 확인할 실험은 설계하지 못했습니다.
